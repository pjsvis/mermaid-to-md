## What was learned

- **Brief rot is the same feedback-path gap as doc rot.** Debriefs 003 and 004
  caught doc-rot (stale `about.md`/`README.md` after the wrapper shipped) and
  built `check-docs.sh` as the structured feedback path — "make forgetting
  expensive." Brief 007 rotted the same way: implementation and documentation
  happened in different sessions, the turn boundary dropped the "update the
  brief" thread, and the brief sat stale. The difference: `check-docs.sh` can
  grep for stale-marker phrases in standard docs; there is no equivalent check
  for stale briefs because briefs are working documents, not shipped documents.
  The structural fix for brief rot is the debrief itself — writing it forces
  the cross-check between brief status and git reality. A brief without a
  closing debrief is a brief at risk of rot.

- **Evidence first, document second.** I initially listed B1 as a "what I'd
  watch" item because brief 007 listed it as open. The correct order is:
  reproduce the bug (is the demo actually broken?), check git log (was there a
  fix commit?), read the decision (what was the resolution?), then read the
  brief (does it agree?). Trusting the brief's stated status over the git
  evidence is the same map/territory error as the cargo-install mistake in
  debrief 003 — categorising by what the document says (the map) rather than
  what the code does (the territory). A brief is a map. Git log + test run is
  the territory. When they disagree, the territory wins.

- **Commit discipline ≠ bookkeeping discipline.** All three resolution commits
  referenced brief 007 and item codes — exemplary. But none of them edited the
  brief itself to check a box or update the status. The commit messages
  documented the resolution *to the commit history*, not *to the brief*. The
  brief is a coordination artifact, not a git artifact; updating it is a
  separate step that no commit hook can enforce. The gap is the debrief — the
  checkpoint where the map is brought back into alignment with the territory.

- **The bar for a session debrief is lower than a project debrief.** This
  session produced zero code changes. The artifact is the cleanup itself
  (retired brief) plus the lesson (evidence-first). That's worth recording,
  because next time a brief disagrees with git, the debrief exists as the
  worked example of what to do: reproduce, trace the commits, update the brief,
  write the lesson.
