# debrief: session 2026-07-25 (III) — the cargo-install category mistake

**Session:** 2026-07-25, ~14:00–14:25 (the afternoon block after debrief 002)
**Epic:** none — a documentation correction
**Result:** small but clean — one factual error caught and fixed, one reusable lesson captured

## What happened

1. **Caught a category mistake in `DEPENDENCIES.md`.** The Linux and Windows
   sections (written unverified during debrief 002's session) claimed `cargo
   install glow` would install the markdown viewer. It does not: the `glow`
   crate on crates.io is an unrelated OpenGL bindings library ("GL on
   Whatever"), and Charm's glow is a Go binary. `cargo install glow` fetches
   the wrong package (and as a library crate, likely has no installable
   binary at all). `cargo install just` was correct — `just` is a Rust crate
   — and kept as-is. `5548e0d`.

2. **Verified against the authoritative source.** Fetched the official
   `charmbracelet/glow` README and replaced the cargo lines with canonical
   Charm distribution methods — `brew`/`pacman`/`snap`/Charm apt+yum repos
   /`go install …/glow/v2@latest` (note the **v2** module path) for Linux;
   `winget`/`scoop`/`choco`/go install for Windows. No non-Charm clones
   referenced — the `charmed-glow` Rust port was deliberately omitted (see
   lesson 3).

## What was learned

- **Unverified cross-platform docs default to the author's familiar
  mechanism.** The error wasn't carelessness; it was structural. A
  Rust-shop author documenting untested platforms reaches for the tool they
  know (cargo) and applies it uniformly. The macOS section used `brew` for
  both `just` and `glow` — brew is language-agnostic, so the language
  difference (Rust vs Go) stayed invisible. The Linux/Windows sections
  switched to `cargo`, which is *not* language-agnostic, and the difference
  became a silent error. **Lesson: when an unverified section changes
  mechanism, re-derive each tool's install path from its authoritative
  source — do not copy the sibling tool's path.**

- **Surface similarity is not install similarity.** `just` and `glow` are
  both "modern terminal CLI tools," but one is Rust and one is Go. Grouping
  them by surface category and documenting a shared install path is a
  map/territory error. The territory is the toolchain; the map ("terminal
  tools") hid it.

- **Do not solve the author's familiarity problem at the user's expense.**
  Pointing a Go tool's users at a Rust clone (`charmed-glow`) so the doc
  could stay cargo-flavoured would optimise for the author's comfort, not
  the user's task. The user wants Charm's glow; the doc sends them to
  Charm's glow. The right fix moved the doc toward the user, not the user
  toward the author's toolchain.

- **The "contributing: unverified" framing cuts both ways.** Debrief 002's
  honest "not yet verified from this repo" was good practice — but it also
  let the wrong `cargo install glow` sit unchallenged, because no one had
  run it. Unverified docs rot quietly. The framing's value is as a *pressure
  valve* (inviting platform users to verify and PR), not as a substitute for
  citing the authoritative source. The fix cites the upstream README — the
  right confidence level for instructions you have not run yourself.

- **Blast radius was low, which is why it survived.** glow is optional (the
  doc says `cat` suffices), so a broken install path did not block the
  tool's value proposition. Low-blast-radius errors are the ones that
  persist — nothing forces their correction. Worth flagging when spotted,
  even when "not load-bearing."
